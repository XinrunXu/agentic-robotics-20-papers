Code as Policies: Language Model Programs for Embodied Control

先记住这组证据

未见指令与属性的仿真长程任务：CaP 80%，自然语言规划器 64%；空间几何任务为 62%。

看方法看实验看消融与边界做研究练习

01这篇要解决什么？

如果接口只有“抓”和“放”，自然语言列表很难精确表达“把积木均匀排成对角线”。CaP 把程序作为中间表示：模型负责组合规则，Python 和数值库负责准确计算，机器人 API 负责感知与执行。

02方法怎样运转？

  1. 01

    暴露感知和控制 API

    例如查询物体坐标、检测边界框、执行抓放。输入是自然语言指令和示例代码，输出是可运行的 language model program。

  2. 02

    用代码表达行为

    生成循环、条件、数组运算和第三方库调用，计算目标点，再将点传给动作接口。几何计算不必全靠语言推理。

  3. 03

    递归补全函数

    主程序调用尚未定义的辅助函数时，继续让模型生成其定义。这个层次化过程帮助分解复杂代码。

方法与结果的原文定位见本页引用。

03跟着一个例子想一遍

教学推演

教学推演：“把三个积木等间距摆在两只碗之间。”先感知两只碗的位置 a、b，再计算 a 与 b 之间的三个插值点，最后逐一抓放。模型提出插值和循环的结构，数值库算出准确坐标；机器人是否能稳稳抓住积木仍由已有抓放接口决定。

怎样读这组数字

代码的优势在需要精确计算与组合的新指令上比较清晰。RoboCodeGen 的 95% 是程序单元测试通过率；摘要里的 HumanEval 39.8% 同样是编程指标，均不能替代机器人任务成功率。

05收益来自哪里，又停在哪里？

消融与机制证据

表 I 在相同模型内对照平铺和层次化生成，davinci 从 81% 到 95%。这支持函数分解的作用，但不同模型改善幅度不同；小模型未必能可靠管理更复杂的函数层次。

结论的适用边界

高层抓放 API 隐含了大量工程能力。读代码时必须圈出模型生成的部分和人工提供的部分；示例可运行，也不意味着碰撞、接触与控制误差已解决。

07把阅读变成一个小研究

讲义提出的研究练习 · 不是论文复现结果

固定模型与任务，把 pick_and_place 分别换成高层抓放、末端位姿 + 夹爪两套接口，观察成功率如何变化。

先自己回答：这项实验怎样才有解释力？

把失败拆成代码错误、几何错误和控制失败。若高层接口大幅提升结果，说明抽象本身贡献了能力；不应把全部收益归因于模型更会推理。

合上原文后，试着回答
  1. 用自己的话说出这篇改变了哪个模块。
  2. 画出它的输入、输出和一次失败如何被处理。
  3. 复述一个结果，同时说清基线、指标与实验条件。
