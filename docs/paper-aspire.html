看方法看实验看消融与边界做研究练习

01这篇要解决什么？

机器人程序报错时，“任务失败”通常不够用。到底没看见目标、导航点不可达，还是夹爪抓偏？ASPIRE 为 coding agent 提供逐原语的多模态执行记录，让它检查因果链、修改程序，再将经过验证的修复方式存入技能库。

02先看一个场景

具体情境 · 先有画面，再看机制

任务是 BEHAVIOR-1K 里的导航取收音机。机器人已经检测到收音机，却反复靠不过去。此时只知道“任务失败”没有用：是没看见、导航点不可达，还是抓偏了，对应的修法完全不同。

03方法怎样运转？

  1. 01

    把程序放进一个留下逐调用证据的执行环境

    ASPIRE 自己不训练机器人模型：程序由现成的 coding agent 写（仿真部分全程是 Claude Code 搭 Claude Opus 4.6、1M token 上下文；真机换成 OpenAI Codex GPT-5.5），程序只能调用 CaP-X 框架预先给定的感知、几何与运动规划 API，感知端接的是 SAM3 文本提示分割、VLM 指点这类现成服务。执行引擎为每一次原语调用留下一条记录：调用了哪个 API、输入与输出、返回状态，以及相关的多模态证据——该调用前后各一帧图像与叠加图、抓取候选、物体位姿、运动规划结果。代理拿到的不是整段视频，而是围绕可疑调用的这些片段，因此能顺着返回状态往回找是哪一环先坏。

  2. 02

    定位失败、改程序、在调试分片上重跑验证

    代理不重写整段任务程序，而是先从 trace 里认出出错的原语，再写针对性的修改，并只在调试 seed 上重跑确认。评测 seed 在调试期间被锁住，最终程序在其上只跑一次，这条协议由 agent 提示直接规定。系统提示同时禁止读取仿真器真值：物体位置、任务判定谓词、场景资产文件都算违规，诊断必须出自观测与 trace，理由是这些通道在真机上不存在。

  3. 03

    用进化搜索跳出局部补丁

    沿单条轨迹反复打补丁容易困在同一个坏思路上。每一轮，coding agent 基于技能库、历史表现最好的前三个程序以及它们残留的失败 trace，提出 K 个候选程序，逐个送进执行引擎打分；下一轮再条件在新的最优程序与它尚未解决的失败模式上。终止条件有两个：某个候选在调试配置上达到阈值，或者搜索预算用尽。搜索还维护一份跨轮的任务分析文档，记下场景描述、正在检验的假设、已经被实验排除的方向，以及因工作空间限制暂时走不通、但将来有新手段可以再试的方向。

  4. 04

    只有验证过的修复才升级成技能

    actor 按固定字段汇报：观察到的失败模式、验证过的修复、可迁移的模式、任务特有的怪癖，以及在调试配置上的验证成功率。协调者审这份汇报，确认修复没有违反 API 政策、而且能迁移出原任务，才把它写进共享技能库；多个 actor 并行跑，但技能写入由协调者串行化。技能条目存的是失败特征、何时适用的触发条件、修复策略，必要时附一段代码草图——落地形式就是 coding agent 的技能文件加一份记忆索引，新任务开工前先读索引再读相关技能。

04跟着这个场景走一遍

原文案例解读

原文 §2.1 的收音机案例正好把这四步走了一遍。第一步，任务是 BEHAVIOR-1K 的导航取收音机；自我视角关键帧显示机器人找到了收音机却反复靠不过去，而执行引擎已经把这段过程拆成逐调用的记录留在那里。第二步，代理顺着记录读返回状态：感知调用成功并给出了收音机位姿，问题出在随后多次 navigate_to_pose 都返回 PLANNING_ERROR；再看日志里的导航目标点，它落在离桌沿约 20 厘米的范围内（这是论文给出的数值），触发避障，规划器因此判定不可达。这一步的结论是失败既不在检测也不在抓取，而在目标位姿本身不可行。第三步，修复顺着诊断写：不动感知提示、也不动抓取原语，而是加一段多角度接近例程，在收音机周围采样别的导航目标，挑一个能绕开碰撞缓冲的方向靠过去，再重新感知并完成抓取；这段修改要在调试配置上重跑通过才算数，评测 seed 此时仍是锁住的。第四步，写进技能库的不是这台收音机在哪个坐标，而是一条导航恢复模式：当采样目标落进障碍物边界的碰撞缓冲、规划器反复报错时，先在物体四周换接近方向，再重试感知与抓取。协调者确认它不依赖本任务、也没有绕过 API 政策，才把它升级成技能。这套机制没做到的事也要看清：它不改动任何控制器权重，能表达的修复被预先给定的 API 圈住；技能库变大之后，过时、过细或误导性的条目如何淘汰与再验证，论文自己列为尚未解决的问题。

05实验到底表现怎样？

LIBERO-Pro 报告位置与指令扰动，并采用留出的 50 个评测 seed；另在 LIBERO-90 积累技能后，对 LIBERO-Pro Long 做不再调试的迁移。真实实验比较有 / 无技能，并同时报告成功率和 token。

怎样读这组数字

执行证据引擎带来的跳升最大，说明“能看清哪里坏了”是关键条件；进化搜索再解决一部分残余难题。长程迁移 30.5% 是另一种更难的协议，不能用 72% 代替。

06收益来自哪里，又停在哪里？

消融与机制证据

§3.7 区分引擎与进化搜索；附录表 5 还显示技能来源从 0、25、50 到 90 项任务时，长程总体为 4.7%、13.7%、21.5%、30.5%。积累的覆盖重要，但需计入训练任务上的调试成本。

结论的适用边界

模型来源与前提成本要分开算：ASPIRE 不训练任何模型。机器人侧用的是 CaP-X 预先给定的感知、几何与运动规划 API（感知服务里包含 SAM3 文本提示分割等现成模型），智能侧用的是冻结的前沿 LLM——仿真实验全程 Claude Code 搭 Claude Opus 4.6，真机换成 Codex GPT-5.5。论文自己列出随之而来的四条限制：没有验证更小或更弱的模型能否撑住同一套调试循环；能表达的修复被固定 API 圈住，超出范围只能低效逼近或等人扩接口；技能库变大后会出现过时、过细、冗余或误导的条目，缺少成熟的检索、剪枝、排序与再验证，这也能解释零样本迁移的非单调；整个调试与搜索循环消耗大量 LLM 调用与 rollout。技能可以是自然语言修复知识，不一定是独立可执行控制器。真实开 / 推抽屉使用技能后仍只有 11/20；自动复位、成功判断与长时间自主运行仍有工程限制。

先自己回答：这项实验怎样才有解释力？

一条可迁移的教训应有适用条件和已验证证据。若只记某个 seed 的坐标，很可能是实例记忆；要通过留出布局才能证明更一般的技能。

先自己答，再看前两问的参考答案

这篇改了哪个模块改动落在经验的存放位置，以及为沉淀经验所必需的执行环境。机器人侧的感知、几何与运动规划都是 CaP-X 预先给定的 API，程序由现成的 coding agent 写，控制器权重一律不动，动作的输出形式也还是那套 API 调用。真正换掉的是两件事：让执行引擎为每一次原语调用留下记录与多模态证据，使得“哪一环先坏”成为可查的事实；再把一次已验证的修复从“这次怎么绕过去的”升级成技能库里带触发条件的条目，于是被积累下来的是修复知识，而不是某个 seed 的坐标。

输入、输出与一次失败如何被处理输入是任务描述、CaP-X 固定的 API 列表，以及开工前先读的记忆索引与相关技能条目；运行中真正供诊断用的输入是逐原语的执行记录——调用了哪个 API、输入与输出、返回状态，外加围绕可疑调用的多模态证据，包括该调用前后各一帧图像与叠加图、抓取候选、物体位姿与运动规划结果，代理看到的是这些片段而不是整段视频。被明确禁止的是仿真器真值：物体位置、任务判定谓词、场景资产文件都算违规，评测 seed 在调试期间锁住，诊断必须出自观测与 trace。输出有两级：一是针对出错原语改过的程序，只在调试 seed 上重跑确认，最终程序在留出 seed 上只跑一次；二是经协调者审核后串行写入共享技能库的条目，内容是失败特征、何时适用的触发条件、修复策略与必要的代码草图，落地形式就是 coding agent 的技能文件加一份记忆索引，交给后续任务的程序合成使用。失败由代理自己发现，依据是 trace 里的返回状态与前后帧证据：收音机那次是感知调用已经给出位姿、而多次 navigate_to_pose 返回 PLANNING_ERROR，据此判定坏在导航目标位姿而非检测或抓取，修法是加一段多角度接近例程并在调试配置上重跑通过；若沿单条轨迹反复打补丁仍走不出去，进化搜索会基于技能库、历史表现最好的前三个程序与它们残留的失败 trace 另提一批候选，并把已被实验排除的方向写进跨轮的任务分析文档。
