RoboOS: A Hierarchical Embodied Framework for Cross-Embodiment and Multi-Agent Collaboration

首发 2025-05-06精读版本 v2阅读原文 ↗
先记住这组证据

多机器人规划工具调用准确率：RoboBrain-7B-1.5-OS 81.74，DeepSeek-V3 76.21；这不是协作实机成功率。

看方法看实验看消融与边界做研究练习

01这篇要解决什么？

一个机器人能规划，不代表两个机器人就能有效配合。RoboOS 把认知、技能执行和共享记忆拆开，以统一的机器人与工具描述连接异构本体。读这篇要理解任务分配依据和同步过程，而不只记“具身操作系统”这个名字。

02先看一个场景

具体情境 · 先有画面，再看机制

按论文餐厅演示的配置，一台 Unitree G1 人形与一台 Agilex 双臂机器人协作处理“我饿了，来一个普通汉堡”。两台机器人本体不同、技能不同，还必须知道对方做到哪一步。把两个各自会规划的 Agent 放在一起并不够：任务依赖、世界状态与各自能力都得是共享的。

03方法怎样运转？

  1. 01

    先固定接入格式：Robot Profile 与小脑技能库

    Cerebellum Skill Library 部署在各机器人终端，通过标准化的 Robot Profile 与工具描述接入系统。库里的工具基本都是现成组件：操作侧包含专家式抓取（AffordGrasp、AnyGrasp）与 VLA 类策略（OpenVLA、RDT-1B、Octo、π₀），导航侧包含传统的建图—定位—导航管线（SLAM）与视觉语言导航工具（MapNav、NaVid），另有灵巧手、接触密集与柔性物体等专用技能。RoboOS 自己不训练这些底层技能，它规定的是接入格式与调用接口。

  2. 02

    大脑：在 Qwen2.5-VL-7B 上三段训练出的 RoboBrain-1.5-OS

    论文明说云端大脑可以换成任意 MLLM，而作者自己训练的版本是 RoboBrain-1.5-OS：以预训练 Qwen2.5-VL-7B 为底座做全参数训练，Stage-1 用 300 万条通用 VLM 数据建立感知与推理，Stage-2 用 230 万条机器人数据（规划、指点、可供性、轨迹四类能力）并保留 10% 的 Stage-1 数据防遗忘，Stage-3 先用 245K 的 OS-SFT 样本，再对 4K 条纯工具调用样本做 GRPO。Stage-3 的数据是合成的：用 DeepSeek-V3-0324 在超市、家居、餐厅三类场景的 68 种协作任务类型上生成 Multi-Robot-45k（每条含场景图、机器人规格与长程协作任务，答案是推理过程与子任务工作流图），再派生出带概率注入错误负样本的 Robotic-Agent-144k。

  3. 03

    分解：先检索共享记忆，再产出带依赖的子任务图

    收到全局指令 T_global 后，RoboBrain 先对共享空间记忆做一次 RAG 检索得到环境信息 M_s，再与时序记忆里的历史执行反馈 M_t、各机器人状态 S_r（空闲 / 忙碌 / 离线）、技能库 M_r 一起拼接输入，输出一段推理轨迹和一张子任务图 G。共享记忆的空间部分是分层动态场景图（楼层—房间—物体三级节点，边表示空间或功能关系），由多视角 RGB-D 经 SAM 分割与 CLIP 特征构建，再用几何聚类与开放词表 grounding 合并，整体由 Redis 承载。

  4. 04

    调度：Monitor 按拓扑深度决定并行还是阻塞

    G 是有向无环图，每个子任务标注执行深度 d 与承担者，分两类：单机器人子任务 (d, r_i) 和需要多台协同的协作子任务 (d, r_{i:j})。Monitor 对同一深度的独立子任务做并行下发，对深度 d+1 的子任务做顺序阻塞——它要等 d 层的全部前置完成才解锁。系统还支持同时管理多张子任务图，以应对机器人状态和任务依赖的动态变化。

  5. 05

    执行与回写：每个子任务一个 Agent，记忆随动作增量更新

    每个子任务配一个专属 Robotic Agent，依据三样东西自行从技能库选工具：此前执行的反馈、工具调用历史、以及环境的局部空间记忆。论文给的例子是“找一个鸡蛋并放到桌上”——厨房里没检测到鸡蛋时，Agent 用空间记忆推断冰箱这类可能位置，改调导航工具过去，这就是它所谓的闭环恢复。动作产生的效果实时改写场景图的节点属性与空间边（如把杯子放上架子后更新位置与支撑关系），并做遮挡与历史感知的修正；反馈与工具调用记录写入时序记忆，关节与电量等状态写入机器人记忆，共同影响下一轮调度。

04跟着这个场景走一遍

教学推演

教学推演：回到上面的场景。第一步，两台机器人在注册时各自提交 Robot Profile，人形挂着导航与搬运类工具，双臂挂着 VLA 类抓取工具；大脑看到的是这些标准化描述，而不是各自的关节接口——换一台新本体意味着补一份 Profile 和一批已接入技能，不是零适配。第二步，大脑是 RoboBrain-1.5-OS。它之所以能直接输出“谁做哪一段”，不是因为通用 VLM 天然会分工，而是因为 Stage-3 专门用 DeepSeek-V3 合成的多机协作与工具调用数据训过；换成未经这类训练的模型，表 1 里的差距就是代价。第三步，大脑先 RAG 检索空间记忆确认食材与餐盘在哪、时序记忆里上一轮做到哪、两台机器人当前是空闲还是忙碌，然后吐出子任务图：备餐在人形侧，取餐与递送在双臂侧，递送依赖备餐完成。第四步，Monitor 看拓扑深度——备餐与擦拭台面同在第一层可以并行，递送在第二层被阻塞，直到备餐节点回报完成才解锁。第五步，各子任务的 Agent 自己选工具；若“检测汉堡”失败，Agent 不会硬重试，而是查空间记忆里还有哪些候选位置并改调导航工具，动作结果又立刻改写场景图的节点与边，供下一次调度使用。整套流程里，决定协作成败的其实是第三步和第五步之间的一致性：如果场景图仍把托盘记在厨房，第四步的依赖排序看起来依然流畅，分工却已经错了。这个推演不代表论文测量过这条具体流程，表 1 的 81.74 衡量的也只是大脑侧的工具调用准确率。

怎样读这组数字

81.74 衡量的是规划 / 工具调用层面的表现。论文同时提供跨本体协作演示，但这个表不能证明多台机器人完整完成真实任务的概率是 81.74%。

06收益来自哪里，又停在哪里？

消融与机制证据

本文主要证据是模型能力比较、系统部署和协作展示；这些不能替代“去掉共享记忆”后的同预算端到端对照。把共享记忆视为架构设计的合理机制，与认定它的独立贡献已经量化，是两件不同的事。

结论的适用边界

模型来源是混合的，读这篇时要把两侧成本分开算。小脑侧全部是现成组件（AnyGrasp、AffordGrasp、OpenVLA、RDT-1B、Octo、π₀、SLAM、MapNav、NaVid 等），RoboOS 不训练它们，只规定 Robot Profile 与工具描述这层接入格式；大脑侧的 RoboBrain-1.5-OS 则是作者在预训练 Qwen2.5-VL-7B 上做的全参数三阶段训练，Stage-1 与 Stage-2 用了 20 台 8×A800 服务器，这是系统真正的前提成本。还要注意表 1 的 81.74 评的是这个自训大脑的工具调用准确率，不是整套系统的协作成功率；换成现成的 DeepSeek-V3-685B 是 76.21，说明这层可替换但有代价。Stage-3 的训练数据由 DeepSeek-V3-0324 合成，评测用的多机规划任务同样是在这三类场景里采样生成的每场景 200 条，论文没有说明两者的生成流程是否完全独立。此外不同机器人仍需已接入的技能和标准化 Robot Profile，跨本体支持不等于任意新机器人零适配；状态冲突、通信延迟和技能前置条件都会影响最终协作。

先自己答，再看前两问的参考答案

这篇改了哪个模块这篇动的不是机器人会做什么，而是多台异构本体之间用什么格式互相看见对方：接入侧被规定成标准化的 Robot Profile 与工具描述，世界状态被收进一份由 Redis 承载的共享记忆，任务依赖、环境事实与各自能力因此成为共用的东西，而不是每台机器人各持一份。它没有训练任何一条底层技能，小脑技能库里的抓取、VLA 策略与导航管线都是现成组件按这层格式接进来的，动作空间与控制器保持原样，本体的能力边界一点没变。自训的部分只在大脑侧的 RoboBrain-1.5-OS，而它学的也是分工与工具调用，不是运动。

输入、输出与一次失败如何被处理输入是全局指令 T_global，加上四样由外部系统备好的东西：RAG 检索共享空间记忆得到的环境信息 M_s、时序记忆里的历史执行反馈 M_t、各机器人当前状态 S_r（空闲、忙碌或离线）、以及技能库 M_r；大脑看到的是这些结构化描述，场景图由多视角 RGB-D 经 SAM 分割与 CLIP 特征在系统侧建好，原始图像流并不直接进它的输入。输出是一段推理轨迹与一张子任务图 G，节点标注执行深度与承担者，分单机器人子任务与需要多台协同的协作子任务，交给 Monitor 按拓扑深度决定并行下发还是阻塞，每个节点再由一个专属 Robotic Agent 从小脑技能库里选工具去执行。失败由该子任务的 Robotic Agent 自己发现，依据是此前执行的反馈、工具调用历史与环境的局部空间记忆，处理方式是换候选位置重试：厨房里没检测到鸡蛋，就据空间记忆推断冰箱这类位置、改调导航工具过去，动作结果实时改写场景图的节点属性与空间边，反馈写入时序记忆，影响下一轮调度。这条通路里没有独立于执行者的验收环节，子任务算不算完成由同一个 Agent 凭自己拿到的工具反馈判定；共享记忆一旦过期，依赖排序看起来依然流畅，分工却已经错了。

多机器人协作需要共享任务依赖、世界状态和各自能力，不能只把多个 Agent 放在一起。
